# Architecture

## Overview

```
Browser ──> Caddy (production) ──┬─ /api/*  → FastAPI (uvicorn) → PostgreSQL
                                 └─ other   → static frontend (Vite build output)

Development: the Vite dev server proxies /api to the backend, so the app is
same-origin in both environments and needs no CORS configuration.
```

- All backend routes live under `/api`.
- **The OpenAPI schema is the contract between frontend and backend.** The backend is the
  source of truth; frontend types in `frontend/src/lib/api/schema.d.ts` are generated by
  `make gen-api` and never written by hand. CI fails if they are out of date.
- One `.env` at the repo root configures everything (backend settings, Vite ports, Docker).

## Repository layout

| Path | Purpose |
| --- | --- |
| `backend/` | FastAPI app, Alembic migrations, pytest suite (uv workspace member) |
| `scraper/` | Course data pipeline for counts.oxy.edu and DB importer (uv workspace member) |
| `frontend/` | React single-page app (npm project) |
| `docs/` | Architecture and design notes |
| `.github/workflows/` | CI |
| `deploy/` | *(planned)* Production Docker Compose, Caddyfile, backup scripts |

Python code is a uv workspace: the root `pyproject.toml` lists `backend` and `scraper`, and
there is a single `uv.lock` and `.venv` at the repo root. The backend is installed as the `app`
package so the scraper's importer can reuse its SQLAlchemy models. Python 3.12 is pinned in the
root `.python-version`.

## Backend

```
backend/app/
├── main.py           create_app() factory: mounts routers under /api
├── core/config.py    Settings (pydantic-settings). The only place that reads env vars.
├── db/base.py        Declarative Base with a constraint naming convention
├── db/session.py     Engine, SessionLocal, get_db dependency
├── api/router.py     Collects all route modules
├── api/routes/       HTTP layer: parse input, call a service, return a schema
├── services/         Business rules (validation, lockouts, anonymous review tokens…)
├── models/           SQLAlchemy models (import each module in models/__init__.py)
└── schemas/          Pydantic request/response models
```

Rules of thumb:

- Routes stay thin. Anything that is a product rule goes in `services/` so it can be tested
  without HTTP.
- Routes return Pydantic schemas, never ORM objects, so the API contract is explicit.
- Schema changes go through Alembic: edit models, then `make migration m="..."`, then review the
  generated file.
- Sync SQLAlchemy with psycopg 3. That is plenty for a few thousand users and keeps the code simple.

## Scraper

```
scraper/oxy_scraper/
├── client.py      CountsClient: WebForms postbacks, >=1 s between requests, retry/backoff
├── fetch.py       Step 1: list + detail pages -> data/raw (cached, resumable)
├── parsed.py      Step 2: data/raw -> data/parsed/<term>.json (offline)
├── parse.py       HTML -> rows and details (pure functions, tested against saved fixtures)
├── store.py       data/raw layout (gzip HTML + meta.json per term)
├── exclusions.py  Listings that never become courses (scraper/overrides/exclusions.csv)
└── cli.py         python -m oxy_scraper <command>
```

counts.oxy.edu is an ASP.NET WebForms page that keeps its state in `__VIEWSTATE`, so a saved
page can be replayed later to post back from it. The fetcher asks for one subject at a time, and
only for subjects in that term's own dropdown (empty subjects make the server return HTTP 500).
Detail popups are fetched once per term per (dept, number, title), so description changes are
kept; for topic courses ("Special Topics"/"Topics in" titles, or "Topics vary" in a
description) every section in every term is fetched. Labs listed under a lecture ("COMP 131 1-1")
are grouped by their own title, because some departments give them their own description. The
fetcher stops after 5 failures in a row; rerunning resumes where it stopped.

The parse step writes one JSON file per term: every listed row as shown (instructors with full
names, meetings, core, seats) plus the parsed popups keyed by CRN (description, restrictions,
prerequisites, corequisites, reserved seats). Each section's `detail_crn` names the popup that
describes it; `detail_shared` is true when that popup was fetched for another section of the
same course. Popups contain no rooms and no textbook list.

## Frontend

```
frontend/src/
├── app/                 App root: providers (TanStack Query), router
├── styles/theme.css     ★ Design tokens: colors, radius, fonts (light + dark)
├── styles/index.css     Tailwind entry + base styles
├── components/ui/       shadcn/ui primitives (owned source, edit freely)
├── components/layout/   AppShell, SiteHeader, SiteFooter, PageContainer
├── components/          Shared composites used across features (e.g. Combobox)
├── features/<domain>/   One folder per domain: pages, components, api.ts (query hooks)
├── lib/api/             Typed fetch client + generated OpenAPI types
├── lib/query-client.ts  TanStack Query defaults
└── test/setup.ts        Vitest setup
```

Data flow: `page → feature hook (features/*/api.ts) → apiGet() → /api/...`.
Pages never call `fetch` directly.

## How to restyle

The UI is built in layers, so most visual changes touch one place:

| Change | Edit |
| --- | --- |
| Colors, radius, fonts, dark mode | `src/styles/theme.css` only |
| Look of buttons, inputs, cards… | the primitive in `src/components/ui/` |
| Header, footer, page width, overall layout | `src/components/layout/` |
| A single page's arrangement | that page in `src/features/<domain>/` |

Conventions that keep this working:

- Use semantic utilities (`bg-primary`, `text-muted-foreground`, `border`, `rounded-lg`).
  Don't use raw palette classes such as `bg-blue-500` or hard-coded hex values.
- Feature pages compose `components/ui` and layout components. Visual styling belongs in the
  primitives, not in pages.
- Data fetching lives in `features/*/api.ts` hooks, so a redesign never touches data logic.
- New shadcn components: `cd frontend && npx shadcn@latest add <name>`. They pick up the tokens
  automatically.

## Testing

- Backend: pytest against a real Postgres (Docker locally, a service container in CI).
- Frontend: Vitest + Testing Library for components. Playwright end-to-end tests arrive with the
  browsing pages.
